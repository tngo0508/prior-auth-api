Prior Authorization API: developer guide

For developers of provider systems that will request prior authorization from the plan.

This API lets your system ask whether a service needs prior authorization, see what documentation is required, send a request with that documentation, and get the plan's answer. It uses HL7 FHIR R4 and follows the Da Vinci Prior Authorization Support (PAS) guide. Drugs are out of scope.

1. Get registered

Create an RSA or EC key pair. Keep the private key. Send the plan your public key as a JSON Web Key Set. The plan registers your system and gives you a client_id. Never send a private key; a key set containing one is refused.

2. Sign in

Sign-in follows SMART Backend Services. Read /fhir/.well-known/smart-configuration to find the token endpoint, then post a signed assertion to it:

POST /auth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=system/Claim.write system/ClaimResponse.read
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<signed JWT>

The assertion is a JWT signed with RS384 or ES384 whose claims are:

ClaimValue
iss and subYour client_id
audThe token endpoint URL exactly as published
expNo more than five minutes ahead
jtiA value you never reuse. Each assertion works once.

The answer contains an access_token valid for 300 seconds. Send it on every call as Authorization: Bearer <token>, and sign in again when it expires.

3. Check what needs authorization

GET /requirements lists every service that needs prior authorization and the documentation required for each. GET /requirements?code=H2019 answers for one service; an empty list means no authorization is needed. No token is required.

4. Submit a request

POST /fhir/Claim/$submit with Content-Type: application/fhir+json. The body is a FHIR Bundle of type collection containing:

ResourceWhat we read
Claim (required)use must be preauthorization. identifier[0].value is your request number. insurer is required. item[0].productOrService.coding[0].code is the service code. All elements FHIR itself requires must be present.
PatientThe member's name.
DocumentReference (zero or more)Supporting documents, sent inline in content.attachment.data. Accepted types: PDF, JPEG, PNG, TIFF, plain text. Up to 5 MB each and 10 per submission. Links are not accepted.

The answer is a Bundle whose first entry is a ClaimResponse. Read the decision from the review action code in item[0].adjudication[0].extension:

CodeoutcomeMeaningAlso look at
A4queuedPended. A reviewer has not decided yet.communicationRequest, if the reviewer needs more information
A1completeApproved.preAuthRef (authorization number), preAuthPeriod.end
A3completeDenied.disposition (the specific reason)
NAcompleteNo authorization is required for this service.

Sending the same request number again returns the current answer; it does not create a second request.

5. Get the decision

A person reviews every request, so the first answer is normally "pended". Ask again with POST /fhir/Claim/$inquire, sending a Bundle whose Claim carries the same request number, or read GET /fhir/ClaimResponse/{id}.

6. Answer a request for more information

When the reviewer needs something, the response Bundle includes a CommunicationRequest whose payload.contentString says what is missing. Send the request again to $submit with the same request number and the missing DocumentReference resources. The request returns to the review queue.

Errors

StatusMeaning
400The body is not valid FHIR, or breaks a rule above. The body is an OperationOutcome that says why.
401No token, an expired token, or a refused sign-in.
403The token lacks the needed scope, or your registration is no longer active.
404No such request among the ones your system sent.

Machine-readable descriptions

/fhir/metadata is the FHIR CapabilityStatement. /fhir/.well-known/smart-configuration describes sign-in.
