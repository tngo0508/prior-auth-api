Prior Authorization API: developer guide

For developers of provider systems that will request prior authorization from the plan.

This API lets your system ask whether a service needs prior authorization, see what documentation is required, send a request with that documentation, and get the plan's answer. It uses HL7 FHIR R4 and follows the Da Vinci Prior Authorization Support (PAS) guide. Drugs are out of scope.

1. Get registered

Create a key pair: RSA of at least 2048 bits (for RS384) or EC on curve P-384 (for ES384). Keep the private key. Send the plan your public key as a JSON Web Key Set in which every key has its own kid. The plan registers your system and gives you a client_id. Never send a private key or a shared secret; a key set containing one, or a symmetric (oct) key, is refused.

2. Sign in

Sign-in follows SMART Backend Services. Read /fhir/.well-known/smart-configuration to find the token endpoint, then post a signed assertion to it:

POST /auth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=system/Claim.c system/ClaimResponse.rs system/Questionnaire.rs
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<signed JWT>

SMART v1 scope names work too: system/Claim.write, system/ClaimResponse.read, system/Questionnaire.read. The token response echoes the scopes as you spelled them. system/Claim.c allows submit and inquire, system/ClaimResponse.rs reading answers, and system/Questionnaire.rs (or system/questionnaire.rs) the DTR endpoints.

The assertion is a JWT signed with RS384 or ES384. Its header carries the kid of the registered key that signed it (it must match exactly one key) and, if present, typ JWT. Its claims are:

ClaimValue
iss and subYour client_id
audThe token endpoint URL exactly as published
expNo more than five minutes ahead
jtiA value you never reuse. Each assertion works once.
iatOptional. If present, not in the future.

The answer contains an access_token valid for 300 seconds. Send it on every call as Authorization: Bearer <token>, and sign in again when it expires. A refused assertion gets 401 invalid_client with the same message whatever the reason. This server offers only SMART Backend Services; the authorization_endpoint in the discovery document exists because SMART requires it, and always answers 400.

3. Check what needs authorization

GET /requirements lists every service that needs prior authorization, with its code system, and the documentation required for each. GET /requirements?code=H2019 answers for one service; add &system= to match the code system exactly. An empty list means no authorization is needed. No token is required.

4. Submit a request

POST /fhir/Claim/$submit with Content-Type: application/fhir+json. The server speaks FHIR JSON only: a non-JSON body gets 415, and asking for XML with Accept or _format gets 406. The body is a FHIR Bundle of type collection, sent directly or wrapped in Parameters under resource, whose first entry is the Claim. One request is for one service. It contains:

ResourceWhat we read
Claim (required)Exactly one. status must be active and use preauthorization. identifier[0] (system and value, each at most 200 characters, no leading or trailing spaces) is your request number. insurer is required. item has exactly one entry, whose productOrService.coding carries the service code and its system (HCPCS or CPT). patient must reference the Patient in the Bundle. No modifierExtension: update and cancel are not supported. All elements FHIR itself requires must be present.
Patient (required)The one Claim.patient points to, by fullUrl or type and id. The member's name and first identifier.
QuestionnaireResponse (zero or more)Answers to the plan's questionnaire for the service. The reviewer sees each question with its answer.
DocumentReference (zero or more)Supporting documents, sent inline in content.attachment.data. Accepted types: PDF, JPEG, PNG, TIFF, plain text. Up to 5 MB each and 10 per submission. Links are not accepted. A body larger than about 71 MB is refused with 413.

The answer is a Bundle whose first entry is a ClaimResponse. Read the decision from the review action code in item[0].adjudication[0].extension:

A request is identified by your system plus the system and value of Claim.identifier. Sending the same request number again for the same member and service returns the current answer; it does not create a second request. Sending it for a different member or service is refused with 422: use a new number.

5. Get the decision

A person reviews every request, so the first answer is normally "pended". Ask again with POST /fhir/Claim/$inquire, sending a Bundle whose Claim carries the same request number (system and value), or read GET /fhir/ClaimResponse/{id}. If nothing matches, $inquire answers 200 with an empty Bundle. Reading by id returns an ETag; send it back in If-None-Match and you get 304 Not Modified until the answer changes, so polling is cheap. The plan does not push notifications.

6. Answer a request for more information

When the reviewer needs something, the response Bundle includes a CommunicationRequest whose payload.contentString says what is missing. Send the request again to $submit with the same request number and the missing DocumentReference resources. If at least one document is new (not identical to one already sent), the request returns to the review queue; a plain retry does not.
