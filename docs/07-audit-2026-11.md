# Audit against the CMS Prior Authorization API workflow (2026-11-11)

This audit checked the service against the CMS-0057-F document *Prior Authorization Application Programming Interface Workflow*. It asked two questions: **are we building the right product** (does the service do what the workflow and the regulation require of the plan?) and **are we building the product right** (does what we built actually work and conform?).

## How it was done

- **Requirements.** Each requirement was pulled from the workflow document, 42 CFR 431.80 and 438.210, DHCS BHIN 26-008, and the Da Vinci CRD, DTR and PAS 2.0.1 guides, CDS Hooks, SMART Backend Services and FHIR R4. Each was then traced to code, tests and docs.
- **Running it.** The service was run and probed with real HTTP on SQLite and SQL Server: malformed input, concurrency, large documents, identifier reuse, time zones and the sign-in edge cases.
- **Validation.** Generated resources were checked with the Firely validator against the published profiles.
- **Review.** Each finding was checked by a second reviewer, and by a critic from the point of view of a regulator, plan operations and an EHR integrator.

## Verdicts

**Right product? Partly.** The FHIR-only, pull-based shape with a human reviewer fits the CMS workflow: CRD on CDS Hooks, DTR packages, PAS `$submit`/`$inquire` and SMART Backend sign-in. But it covers the API surface, not the plan's obligations around it. Those are tracked as issues, and most need agency decisions:
- expedited versus standard priority, decision timeframes and extensions;
- appeals and the annual metrics;
- member and provider identifiers;
- partial approvals and coded denial reasons;
- 42 CFR Part 2;
- the Patient Access feed.

**Built right? Not yet, but much closer.** The audit found real defects. All the ones that needed no agency decision are fixed on the `audit-fixes` branch:
- only the first service line was read;
- a reused identifier returned the old decision under new patient details;
- concurrent approve and deny both succeeded;
- simultaneous retries gave 500;
- SQL Server reads took minutes once documents were attached;
- UTC dates were used instead of plan dates;
- the CapabilityStatement and the DTR draft QuestionnaireResponse were invalid;
- several CRD, DTR and SMART conformance gaps.

The test suite grew from 65 to 190 tests, all passing on SQLite and SQL Server. The service is still **not deployable**:
- the service list is placeholder data (#1);
- staff have no sign-in (#18);
- nothing is hosted (#4, #9).

## Workflow step verdicts (at the time of the audit)

Every step except Step 9 was *partial* before the fixes. Most step-level defects are now fixed; what keeps each step partial is the open issues listed in the findings table.

| Step | Verdict | Why |
|---|---|---|
| Capability: determine whether prior authorization is required | partial | CRD pa-needed and the public /requirements list work. But the list is four placeholder services, and any unlisted, uncoded or second-item service is told 'no-auth' or 'not required'. |
| Capability: identify documentation requirements | partial | Per-service documentation lists and DTR questionnaires are served. The content is invented, and the documentation list never reaches CRD responses. |
| Capability: exchange prior authorization requests | partial | $submit and $inquire work end to end. Items after the first are dropped, reused identifiers are answered from the wrong Claim, concurrent retries give 500, and there is no update or cancel. |
| Capability: receive payer decisions | partial | Decisions can be pulled by $inquire or read. Concurrent decisions can leave contradictory answers, references in the response do not resolve, and 'created' changes on every read. |
| Step 1 | partial | CDS Hooks discovery and SMART Backend Services work. A conformant CDS client that sends its issuer URI as iss is refused, and there is no CORS for browser clients. |
| Step 2 | partial | The coverage-information extension states PA need and the questionnaire. It answers from placeholder data, skips non-ServiceRequest orders, does not check the payer's coverage, and gives no PA answer when coverage is missing. |
| Step 3 | partial | Results return as update systemActions. There are no Instructions or External Reference cards, unchanged orders are re-updated, and malformed requests give 500. |
| Step 4 | partial | $questionnaire-package returns a valid Questionnaire. The draft QuestionnaireResponse fails the DTR profile, there is no CQL pre-population, and warnings and coverage input are ignored. |
| Step 5 | partial | The payer accepts inline documents and QuestionnaireResponses. Structured clinical resources and DTR-QRBundles are stored but never reach the reviewer. |
| Step 6 | partial | Bundles are accepted and pended. Multi-item, identifier reuse, wrong media types and oversized bodies are mishandled. |
| Step 7 | partial | Approve, deny and request-information work for one reviewer. There is no staff authentication, no concurrency control, no priority or deadline, no partial approval, and clinical content is hidden. |
| Step 8 | partial | The decision is available by polling (a deliberate design choice). ClaimResponse has dangling references, an unstable 'created' and no decision date. |
| Step 9 | met | A provider-side step. The payer makes every decision state retrievable only by the submitting client, and the sample client and probes read all states. |
| Required standards (USCDI, FHIR, US Core, SMART App Launch) | partial | FHIR R4 and SMART Backend Services are used. US Core/USCDI conformance is neither declared nor validated, the CapabilityStatement fails two R4 invariants, and the docs omit US Core/USCDI as required standards. |
| Recommended guide: CRD | partial | order-sign and order-select return coverage information. Several CRD SHALLs are unmet: configuration options, card types, source.topic, no repeat updates, order-select limits, primary hooks and invocation logs. |
| Recommended guide: DTR | partial | $questionnaire-package and Questionnaire read work, and the Questionnaire and package validate. The draft QR is invalid; $expand, $log-questionnaire-errors, changedsince, CQL and the v2 scope names are missing. |
| Recommended guide: PAS (including status check, update and cancel) | partial | Submit and status check ($inquire) work, and response Bundles validate structurally. Update and cancel are not implemented, multi-item is dropped, and subscriptions are absent by design. |

## Accepted as is

- **Pull-only (finding 66).** No PAS Subscriptions. Providers poll `$inquire` or read the ClaimResponse. This is a deliberate choice, recorded in the status page.
- **Extra surface (finding 77).** Kept: the public `/requirements` list, order-select support, and SQLite for development alongside SQL Server.

The full audit evidence (requirement matrices, probe payloads and validator output) was kept outside the repository. For each finding, the issue linked above carries the detail and the fix needed.
